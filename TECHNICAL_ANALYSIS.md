## 4. Current 3D Architecture

**User action → UI → state → 3D → geometry → scene → render flow:**

```
Click / hotkey (W/K/V)
  → HotkeyController.tsx / LeftDrawingToolbar.tsx / WallDrawingEngine2D.tsx
  → useDesigner.setTool / handlePrimaryClick / handleFloorClick   (src/store/useStore.ts)
  → walls[], cabinets[], placedItems[], placedCutouts[] update    (Zustand)
  → Viewport.tsx re-renders scene tree
     ├─ WallBuilder.tsx → Wall3D.tsx (CSG) per segment
     ├─ ProceduralCabinetRow.tsx → CabinetLayoutEngine.tsx → BaseCabinet3D / WallCabinet3D / Countertop3D
     ├─ WallAnchoredPlacement.tsx (catalog GLB items)
     ├─ DoorWindowPlacementEngine.tsx (cutout preview)
     ├─ CADWall2D / CADDimensionLines / 2DBlueprintOverlay (2D only)
  → LightingEnvironment / CeilingCap / FloorGrid / CameraController
  → three.js WebGL render
```

Key elements:

- **Canvas**: `Viewport.tsx:92` — `<Canvas shadows dpr={[1,2]} gl={{antialias, logarithmicDepthBuffer}}>`, ACESFilmicToneMapping, PCFSoftShadowMap, `RaycastGuard` wrapper that try/catches raycaster intersections (CSG safety).
- **Scene**: implicit; ground is a 120×120 polished porcelain plane + gloss coat (`Viewport.tsx:113-134`); fog in 3D only.
- **Camera**: dual camera system in `CameraController.tsx` — a 60° `perspectiveCamera` (3D) and an `orthographicCamera` zoom≈30 (2D top-down). Smooth `lerp`-based 2D↔3D transition via `useFrame`; auto-focus dolly onto a selected wall; arrow-key pan/walk; OrbitControls (rotate locked in 2D, `screenSpacePanning`, `zoomToCursor`).
- **Renderer**: three WebGLRenderer defaults + ACES tone mapping, `logarithmicDepthBuffer`, 4096 shadow maps.
- **Controls**: Drei `OrbitControls` (orbital + pan + zoom + damping).
- **Lights**: `LightingEnvironment.tsx` — 2 directional (key w/ 4096 shadows + cool fill), ambient, hemisphere, 5 warm ceiling point lights, 4 under-cabinet LED point lights, procedural `Environment` (resolution 512, `frames={1}`) built from 5 `Lightformer`s (no HDRI file).
- **Shadows**: key directional `castShadow`, PCFSoft, bias -0.0003, radius 3.
- **Materials**: PBR `MeshStandardMaterial`/`MeshPhysicalMaterial`, clearcoat countertop/doors, transmission glass, `toneMapped:false` LEDs. All theme-keyed, cached per theme in `CabinetModel.tsx:79` (`materialCache`).
- **Geometry**: `BoxGeometry` (walls, carcasses, doors), `ExtrudeGeometry` (L-corner chamfers, countertop slab, ceiling slab, panels-with-holes), `ShapeGeometry` (floor polygon), custom `BufferGeometry` (grid + blueprint line segments), CSG for cutouts.
- **Meshes/Groups**: groups per wall segment, per cabinet module, per run; a single `group` for the whole run also carries selection wireframe.
- **Transform/selection**: no TransformControls. Selection is a **blue wireframe overlay box** drawn slightly larger than the item (`WallAnchoredPlacement.tsx:112-117`, `ProceduralCabinetRow.tsx:121-140`) — never draggable/rotatable/scalable in 3D. Walls selectable; cabinet runs selectable; catalog items selectable.
- **Dragging/rotation/scaling**: not implemented. Only *sliding preview* while placing a catalog item along a wall (`WallAnchoredPlacement.tsx`) and drawing polylines. Scale happens implicitly via X-axis GLB scale (width) and slider updates.
- **Snapping**: `geometry.ts` — grid snap 0.25 m, vertex snap 0.2 m, ortho-snap (0/90/180/270°) while drawing, close-distance 0.35 m to close a loop; cutout center clamp within segment.
- **Grid**: `FloorGrid.tsx` — 25 cm minor / 1 m major `lineSegments`, 2D-only.
- **Measurements**: live length readout (m) + typed-length input (`DimensionOverlay.tsx`), CAD dimension lines in feet (`CADDimensionLines.tsx`), feet labels during 2D drawing (`WallDrawingEngine2D.tsx`).
- **Collision/bounding boxes**: none for placement; bounding boxes computed only for UV mapping in procedural geometry and BOM area math (`polygonArea`).
- **Walls/floor/ceiling**: walls = extruded CSG boxes from Y=0 to `ceilingHeight` (2.8 m, 0.15 m thick); floor = plane + closed-room `FloorPolygon` (ShapeGeometry); ceiling = convex-hull extruded slab at `ceilingHeight` (`CeilingCap.tsx`).
- **Cabinets/doors/drawers/shelves/countertops/handles**: see §5.

## 5. Parametric Cabinet System

There are **two parallel systems**, only one of which is live, plus dead code.

### 5a. Parametric cabinet-run system (ACTIVE)
`CabinetLayoutEngine.tsx` `planRunLayout()` (line 84) + `ProceduralCabinetRow.tsx`.

- Draw a **CabinetRun polyline** (store `CabinetRun { points, baseHeight?, wallHeight?, wallElevation?, customMaterialId? }`).
- `planRunLayout` subdivides each segment into fixed **0.8 m modules** (`STD_CABINET_WIDTH`) of base cabinets; leftover gap ≥ 0.05 m → dynamic **filler**; interior left-turns get a **0.9×0.9 m blind L-corner** (`l-corner`, chamfered 45° diagonal door in `BaseCabinet3D.tsx:237`) + 0.65 m upper corner; countertop is one continuous extruded slab from a computed outline polygon (`buildCounterOutline`).
- `BaseCabinet3D.tsx` — solid enclosed box + inset toe kick (0.10 m, recessed 0.05 m) + variant fronts: `double-door` (2 flush doors, vertical edge pulls) or `drawer` (3 stacked drawer fronts) or `filler` or `l-corner`.
- `WallCabinet3D.tsx` — solid (2 doors) or glass (frame + physical glass + interior LED) + optional soffit up to ceiling; `UpperCornerCabinet3D` chamfered.
- `Countertop3D.tsx` — `CountertopOutline` extrudes the outline polygon at `topY`, thickness 0.04 m, overhang 0.02 m.

**Dimension control that actually exists:**
- Width: **NOT user-controllable per cabinet** — fixed at 0.8 m module; only fillers take leftover width. (Placement system items can set `customWidth`.)
- Height: **user-controllable per run** (`baseHeight`, `wallHeight`, `wallElevation` sliders in `PantryInspectorUI.tsx`), and per catalog item (`customHeight`).
- Depth: NOT per-cabinet in the run system (fixed BASE_DEPTH 0.6); per-catalog-item `customDepth`.
- Door thickness / panel thickness / back panel / shelves / drawer count / door gaps: **NOT exposed** in the active system. Panels are visual 0.02 m fronts, `SEAM 0.006`, `PROUD 0.002`, hardcoded.
- Fillers: auto-generated for leftovers and corner side-gaps (0.3 m and 0.25 m bridge panels).
- Countertop: auto, continuous slab.
- Handles: procedural boxes (`Handle`, edge pulls, bar handles).
- Cabinet types: base double-door, base drawer, l-corner, filler, wall solid, wall glass, upper corner, tall pantry/appliance via catalog.
- Sink/cooker cabinets: **not modeled** in the run system (no roles).

### 5b. Wall-anchored catalog placement (ACTIVE)
`lib/catalog.ts` + `WallAnchoredPlacement.tsx`. Items are **GLB placeholder boxes** scaled on X to `width/standardWidth`. Supports `pantry-tower`, `pantry-tower-wide`, `appliance-tower`, `base-unit`, `wall-unit`, `corner-unit`. Width/height/depth/elevation/material editable per item. Still no doors/drawers — the GLBs are plain boxes.

### 5c. Dead code (NOT wired in)
`ShakerCabinetModel.tsx` + `ProceduralBaseCarcass.tsx` + `ProceduralWallCarcass.tsx` + `lib/proceduralGeometry.ts` (`createPanelWithHolesGeo`, `createGroovedPanelGeo`, `getCachedGeometry`, `clearGeometryCache`). These implement true panel-based carcasses (18 mm sides, 6 mm back panels, grooves, 5 mm nail holes, top/bottom stretchers, toe kick). **Nothing imports `ShakerCabinetModel`** — this whole "real furniture" subsystem is orphaned. `getCachedGeometry`/`clearGeometryCache` are likewise never called, so the geometry cache is inert.

**How dimension changes affect geometry:** for the active system — `baseHeight` changes the carcass box height and moves countertop up (`BaseCabinetRun counterTopY = baseHeight`); `wallHeight`/`wallElevation` move wall-cabinet boxes and soffit; catalog `custom*` values scale the GLB instance or re-render the wireframe. There is **no re-planning of module subdivision on dimension change** (module count is a pure function of segment length only).

## 6. Kitchen Layout System

- **Model**: freehand polylines, not walls. `cabinets[]` are independent `CabinetRun` baselines.
- **Wall detection**: `touchesAnyWall()` in `kitchen.ts:123` — if no run segment endpoint comes within 0.35 m of any wall segment, the run is treated as an **island** (no wall cabinets, countertop +0.15 m deep, waterfall edges).
- **Wall-relative positioning**: only for the *catalog* items — `computeWallAnchoredPlacement()` in `placement.ts:73` projects the cursor onto the wall segment, computes the outward normal via cross product, side-flip hysteresis (0.35 m), clamps the slide within segment, offsets back-face by `WALL_THICKNESS/2 + depth/2`, elevation floor (0) or wall (1.5 m), `rotationY = atan2(nx, nz)`.
- **Run alignment/snapping**: none — runs are placed by eye; they do not snap to walls, corners, or other runs.
- **Spacing/fillers**: fillers are auto-inserted only for leftover widths in the subdivision loop.
- **Corner handling**: `planRunLayout` detects interior left-turns (`cross > 0 && turnAngle >= 0.5 rad`) and inserts the L-corner module; trimming `startTrim/endTrim` reserves 0.9 m of each adjacent segment, and `buildCounterOutline` flares a corner square so the slab covers the corner in one piece. **This is corner *geometry***, not corner *ownership/reservation against obstacles*.
- **L/U/straight kitchens**: not classified. Any polyline works visually; U-shapes are just 4-point runs. No "room" concept — walls and cabinet runs are separate things.
- **Overlap prevention / collision / available-space**: **none** (see §11).

## 7. State Management

- **Zustand v4.5.7**, single store `useDesigner` in `src/store/useStore.ts` (693 lines).
- State shape: `walls: Wall[]`, `cabinets: CabinetRun[]`, `placedItems: PlacedItem[]`, `placedCutouts: PlacedCutout[]`, `tool`, `cameraMode`, `theme`, `ceilingHeight`, selected IDs, `activeCatalogItem`, `activeWallId/activeCabinetId` (drawing state), `pending/hover/pointer`, `typedLength/lockedVector`, `past` (undo snapshots, max 50, JSON-clone), `bomOpen/bomRates`, UI flags.
- **Where cabinet data lives**: plain arrays in the store. `CabinetRun` stores only the polyline + 3 height overrides + material id — **the actual cabinet layout (modules, corners, fillers, counters) is recomputed on every render** by pure functions (`planRunLayout`) — it is *derived*, not stored.
- **Propagation**: components subscribe via `useDesigner(selector)`; mutations go through store actions (`handleFloorClick`, `updateCabinetRun`, `placeItemAtPreview`, `placeCutout`, etc.). History push happens before structural edits.
- **3D↔state sync**: one-way — renderer reads state and rebuilds declaratively. There is **no** read-back from the scene to state, no persistence (no localStorage/URL/database), no selector memoization of derived plans (recomputed per component).

## 8. Data Model

All in `src/store/useStore.ts` unless noted:

- **Wall** (line 28): `{ id, points: Vec2[], closed }` — `Vec2 = { x, z }` in meters.
- **CabinetRun** (line 34): `{ id, points, closed, baseHeight?, wallHeight?, wallElevation?, customMaterialId? }`.

- **PlacedCutout** (line 70): `{ id, wallId, catalogId, type: "door"|"window", positionOnWall (0..L), width, height, sillHeight }`.
- **CatalogItem** (`lib/catalog.ts:18`): `{ id, label, kind: "furniture"|"opening", category, model, standardWidth, width, height, depth, elevation: "floor"|"wall", material: "body"|"appliance", openingType?, sillHeight?, hasGlass? }`.
- **ThemePalette** (`lib/themes.ts:24`): full material palette (cabinetBody/Door, wallCabinet/Door, countertop+roughness/metalness, hardware, plinth, crown, glassTint/glassInterior, wallPaint, floor, led + intensity).

## 9. Materials and Rendering

Implemented (all found in source):
- **PBR materials**: `MeshStandardMaterial`/`MeshPhysicalMaterial` throughout. Cabinet bodies/doors use clearcoat (0.15–0.3), roughness 0.32–0.4, metalness 0.04.
- **Countertop**: physical material, clearcoat 0.85, `specularIntensity 1.2`, envMapIntensity 1.4.
- **Glass**: `MeshPhysicalMaterial` with `transmission 0.92`, `thickness 0.5`, `ior 1.52` (cabinet glass) and window glass `transmission 0.97`.
- **Environment/IBL**: procedural `Environment` from Lightformers (resolution 512, single frame) — no HDRI image file. Metallic hardware/appliance get env reflections.
- **Lighting**: directional key (shadowed) + cool fill + ambient + hemisphere + ceiling spots + under-cabinet LEDs.
- **Shadows**: PCFSoft, 4096 map.
- **Tone mapping**: ACESFilmic, exposure 1.35.
- **Fog**: 3D only.
- **Textures**: **none** — every surface is a flat color. `useTexture` is imported in `LightingEnvironment.tsx` but **never called**.
- **Post-processing**: **none** (no @react-three/postprocessing, no SSR/SSAO/bloom/outlines).
- **AO/reflections beyond envmap**: none (no SSR, no planar reflections; countertop/glass rely purely on envmap + clearcoat).

## 10. Geometry Technology

- **BoxGeometry**: walls, carcass boxes, doors, drawer fronts, handles, soffit, selection boxes, cutout subtraction boxes.
- **ExtrudeGeometry**: L-corner chamfer shapes (`BaseCabinet3D`/`WallCabinet3D`), continuous countertop slab (`Countertop3D`), ceiling slab (`CeilingCap`), and multi-layer panels with grooves/holes (`proceduralGeometry.ts`, dead path).
- **ShapeGeometry**: interior floor polygon (`FloorPolygon`), 2D CAD wall fills with door/window holes (`CADWall2D`).
- **Custom BufferGeometry**: grid `lineSegments`, blueprint overlay line segments, `HoverMarker` crosshair.
- **CSG booleans**: `@react-three/csg` for wall door/window cutouts (`Wall3D.tsx`). Subtraction box is over-sized (`CUTOUT_OVERDEPTH 0.1`) for clean through-carves.
- **Custom vertex manipulation**: UV regeneration from bounding box + dominant normal axis; axis-swap of panel coordinates to place grooves on the desired face; per-layer merge via `mergeBufferGeometries`.
- **Optimization techniques present**: single mesh per module (fewer draw calls), `React.memo` on the CSG mesh so booleans only run on commit, geometry cache map (dead), material caching. **No instancing, no BVH acceleration, no LOD.**

## 11. Collision / Overlap System

**NO COLLISION SYSTEM FOUND.**

What exists is *proximity only*, not collision:
- `touchesAnyWall()` — 0.35 m distance check used purely to classify a run as island.
- Cutout placement clamps the opening within its own segment (`clampOpeningCenter`).
- Catalog item slide clamps within the wall segment (`placement.ts`).

There is **no** test for: cabinet-vs-cabinet overlap (two runs can intersect), cabinet-vs-wall intersection, cutout-vs-cutout overlap on one wall, door/drawer swing collision, corner module vs obstacle, or invalid placement. `planRunLayout` never validates against walls or other runs. Two overlapping runs render overlapping boxes with zero feedback.

## 12. Measurement System

- **Internal units**: meters throughout (the whole scene, walls, cabinets). `constants/dimensions.ts` defines `ROOM_HEIGHT 2.8`, `WALL_THICKNESS 0.15`.
- **Live draw length**: `DimensionOverlay.tsx` — meters `toFixed(2)`, plus a **typed-length input** (`B = A + lockedVector * L`) with `Enter` commit.
- **CAD dimension lines (2D)**: `CADDimensionLines.tsx` — per-wall-segment continuous dimension vector on the **exterior** side (centroid/winding logic to pick the outward normal), extension ticks, arrow caps, and a white-backed `21'` feet label. Uses `formatFeet`/`metersToFeet` (`geometry.ts`).
- **2D drawing labels**: `WallDrawingEngine2D.tsx` — feet labels beside live segments.
- **BOM area**: shoelace `polygonArea` on countertop outline (m²).
- **Bounding-box measurements**: not displayed. Selection overlays use approximate catalog dims ±0.05 m.
- **mm/cm/inch conversion**: no in-app unit toggle. Only meters + display-in-feet.
- **Distance calculations**: `dist`, `distToSegment`, `positionAlongWall`, `orthoSnap` in `geometry.ts`/`cutouts.ts`.

## 16. Performance

Actually present:
- `useMemo`/`useCallback` heavily in all 3D components; derived plans memoized on `[points, isIsland]`.
- `React.memo` on `WallCSGMesh` (`Wall3D.tsx`) — CSG re-evaluates only when wall geometry or committed cutouts change.
- **Material caching** per theme (`materialCache`, `shakerCache`) — bounded, no leaks.
- GLTF **preloading** (`preloadCabinetModels`) + `<Suspense>`.
- `dpr={[1,2]}`, `antialias`, `logarithmicDepthBuffer`, PCFSoft, `frames={1}` env (rendered once).
- Dynamic import / code-splitting of jsPDF (`BOMModal`).
- Pointer-move throttling (10 ms) in the drawing engine; raycaster crash guard.
- Geometry reuse via shared material kits and one-mesh-per-module; dead geometry-cache helpers exist but are unused.

Not present: instancing, BVH/frustum culling setup, LOD, texture atlasing (no textures), worker offload, occlusion culling.

## 18. Current Project Strengths

1. **Clean, modern, working 3D foundation**: Next.js + R3F + Zustand is well-structured and compiles.
2. **Parametric run engine is genuinely good**: `planRunLayout` automatically subdivides a polyline into 0.8 m modules, L-corner blind units (with correct 45° chamfer geometry), fillers, and a **single continuous L-shaped countertop slab** with no seams — a hard problem solved well.
3. **CSG wall cutouts**: real boolean door/window carving that updates on commit only, plus smart raycaster crash-guarding.
4. **Excellent rendering quality for the effort**: clearcoat PBR, transmission glass, ACES, PCFSoft shadows, procedural studio environment, theme re-skinning across the whole scene.
5. **Real CAD affordances**: ortho/grid/vertex snapping, typed exact lengths, feet dimension lines, 2D plan with blueprint overlay and dual-camera transition.
6. **Working business layer**: live BOM + cost estimator reusing the same `planRunLayout` math as the renderer, plus branded PDF quotation — consistent quantities.
7. **Discipline**: geometry/materials cached, booleans memoized, jsPDF code-split, pointer throttling.

## 19. Current Project Weaknesses (for a professional kitchen editor)

1. **No collision/overlap system at all** — runs can intersect, cutouts can overlap, nothing is validated.
2. **Cabinets are solid boxes, not furniture** — no true panels, no adjustable panel thickness, no back panels, no shelves, no drawer counts, no door gaps in the *live* path. The code that *does* build real panels (`Procedural*Carcass`, `ShakerCabinetModel`, `proceduralGeometry`) is orphaned/dead.
3. **Fixed module widths** — only 0.8 m modules + leftover fillers; no 300/400/450/600/900 mm standard-grid control, no facade rhythm/front-width solving.
4. **Layout is polyline-only** — runs don't snap to walls; no wall-relative run anchoring; no L/U classification; no appliance roles (sink/cooker/tall) in runs.
5. **No room/interval model** — walls aren't first-class with usable-spans; obstacles (doors/windows) don't reserve space for cabinets; corner ownership vs obstacles is absent.
6. **No real measurement verification** — no plan-vs-built check, no mm display, no per-module dimension labels.
7. **No import/export/persistence** — no save/load JSON, no glTF/GLB export, no CSV, no DXF; closing the page destroys the design.
8. **No AI** and **no backend/database**.
9. **3D manipulation gap** — no transform controls (gizmo), no direct drag/resize/rotate of placed items in 3D; selection is a wireframe box only.
10. **Performance ceiling** — no instancing, no BVH, no LOD; many per-module meshes; countertop recomputes per component; `dpr [1,2]` with big shadow maps could choke on large kitchens.
11. **Placeholder assets** — all "furniture" is scaled GLB boxes with no geometry detail.
12. **End-of-run finish** — no end panels, no visible gola/handleless profiles, no crown/plinths beyond the toe kick.
13. **Units** — meters internally only, no mm workflow that a cabinetmaker expects; no confidence/measured-vs-assumed states.

## 20. Compatibility with `D:\v1 cab`

The reference is a **SketchUp Ruby extension ("Cabinetrix")** plus a **React/Vite "ALU SYS"** app. Its architecture is *measurement-first, interval-based, mm-accurate, ghost→real*; your current app is *meters, freehand polyline, procedural-box, live-preview*. Concept-by-concept:

### 1. FacadeRhythmSolver
- **Compatible?** Yes — it's a pure algorithm (`CBX_FacadeRhythmSolver.rb`): generate front patterns from preferred widths {450,600}, score (filler-over-target ×1000, narrow ×50k, symmetry ×20, dominant deviation ×5, unique-width ×2k, width-change ×500, custom ×2k), `distribute_residual` symmetrically, merge 5 mm-equal pairs into modules.
- **Difficulty**: Medium. Pure math, no SketchUp dependencies — portable to TypeScript almost line-for-line.
- **Where**: new `src/lib/rhythmSolver.ts`, called from a new plan stage *before* `planRunLayout` (or replacing its subdivision), feeding `width` per module.
- **Rewrite needed**: your fixed `STD_CABINET_WIDTH` subdivision in `CabinetLayoutEngine.tsx` would be replaced; `BaseModulePlacement` already carries a `width` you can vary. Your store doesn't need changes.
- **Benefit**: professional-looking facades — equal widths, symmetry, dominant-width runs, 0 mm unresolved gaps instead of arbitrary leftover fillers.

### 2. Wall interval model
- **Compatible?** Yes, but requires adding a **room/wall topology layer** you don't have.
- **Difficulty**: Medium-High. The reference (`CBX_LayoutPlanner.rb`) models each wall as `WallSegment { length_mm, blocked_base[], blocked_top[] }` → `usable spans` → placements. Your `Wall` has only `points`; `PlacedCutout` already gives you blocked intervals you could merge into usable spans.
- **Where**: extend `Wall` in the store (or a derived `useMemo` room model) + `lib/intervals.ts` (merge/find-gaps helpers exist conceptually in `close_all_wall_spans`).
- **Rewrite**: `planRunLayout` would consume *intervals*, not the raw polyline; runs would snap/attach to walls via the `<wallId,start>↔mm` mapping (reuse your `parseSegmentId`).
- **Benefit**: obstacle-aware packing, wall-length closure to 0 mm, real L/U/U-shaped kitchens.

### 3. Corner ownership
- **Compatible?** Yes, partially. You already place an L-corner by turn detection; the reference adds **ownership rules**: corner 1010 mm on one wall + 560/625 mm return on the adjacent wall, with `corner`/`corner_return`/`corner_fallback` zones and obstacle-conflict fallbacks.
- **Difficulty**: Low-Medium (mostly adding conflict checks against cutouts + reserving the adjacent wall's start/end).
- **Where**: `planRunLayout` corner block + `cutouts.ts` (conflict helpers) + store `Wall` blocked intervals.
- **Benefit**: corners never collide with windows/doors; base and top corner returns stay aligned (yours already handles upper corner size 0.65 m, but not the ownership/fallback logic).

### 4. Ghost → Real Build pipeline
- **Compatible?** Conceptually yes, architecturally a shift.
- **Difficulty**: Medium-High. In SketchUp, "ghosts" are model entities carrying `GhostRole/GhostType/GhostWidth` attributes that a builder consumes (`CBX_AutoLayout.generate_ghosts_from_placements` → `CBX_Shotgun V2.rb:2310` reads them). In React you'd instead persist a **committed plan** — an array of `PlacedCabinet` records — and treat the live `planRunLayout` output as *ghosts* that are *frozen* into real records on commit.
- **Where**: store gains a `placedRuns`/`committedLayout` structure; `ProceduralCabinetRow` renders either ghost preview (translucent, already exists) or committed modules.
- **Rewrite**: move derived layout → stored layout on commit; add a `GhostID`-style id per module (`wall#idx#k`).
- **Benefit**: you get undoable, inspectable, measurable, exportable *cabinets* instead of re-derived boxes; enables per-module material/role/width editing and the verification/audit features below.

### 5. Plan vs built measurement verification
- **Compatible?** Yes, and cheap once you have committed plans.
- **Difficulty**: Low. The reference measures real bounding boxes and compares `planW/D/H` vs `realW/D/H` (`CBX_SeniorDev_Debug.rb`, `verify_and_report` → "FLAWLESS MATCH"/"GAPS"). In Three.js use `Box3().setFromObject` + `boxSize` per module vs planned dims; report mismatches in the BOM/UI.
- **Where**: `utils/costCalculator.ts`-style diagnostic module + an on-demand "Verify" panel.
- **Benefit**: catches scaling bugs (e.g. GLB X-scale vs intended width), the #1 trust issue for a planning tool.

### 6. End-panel planning
- **Compatible?** Yes. `plan_end_panels` in `CBX_SeniorDev_Builder.rb` shrinks neighbour boxes 18 mm, adds proud 5 mm end panels on exposed run ends.
- **Difficulty**: Low-Medium (pure 2D interval logic on run ends/corners).
- **Where**: `CabinetLayoutEngine.tsx` — emit `endPanel` placements in `RunLayout`; render thin boxes in `BaseCabinetRun`/`WallCabinetRun`.
- **Benefit**: instantly makes renders look like real kitchen joinery rather than a row of boxes.

### 7. AI → JSON → geometry
- **Compatible?** Yes. Both projects' current AI flow is identical in shape: `cbx_ai_wizard.rb` (Gemini/GPT-4o → JSON array → `build_from_json`) and ALU SYS `server.ts /api/generate-layout` (Gemini → `{elements, reasoning}` → UI).
- **Difficulty**: Medium (needs a backend or an API-key proxy — you have none). The Ruby side is a template for your system prompt + JSON contract.
- **Where**: new `src/app/api/generate-layout/route.ts` (Next route handler) + a store action `applyAiPlan(placements)` that writes into `placedRuns`/`placedItems`.
- **Rewrite**: your `CabinetRun`/`PlacedItem` shapes must be the JSON contract; the AI would emit wall-anchored placements you can already render.
- **Benefit**: prompt-to-layout; your existing `WallAnchoredPlacement` + BOM make the result immediately quotable.

### 8. Hardware/cost estimation
- **Compatible?** Partially — you already have `costCalculator.ts` (line-item, tax, labor, PDF). The reference goes deeper: **per-part CNC quantities** — edgeband meters (L/C profiles, gola), sheet nesting count (guillotine bin packing), hinges = doors×2, screws = cabinets×20, legs = base×4, glass-door count, gola meters, granite ft² from top faces (`cbx_cnc_pipeline.rb`, `cbx_full_estimate.rb`, CSV export).
- **Difficulty**: Medium. Needs the real-panel model (§19 #2) and per-module parts to count hinges/edgeband; nesting is a self-contained algorithm you can port.
- **Where**: extend `costCalculator.ts` + `BOMModal`; optionally CSV export (easy, or reuse jsPDF).
- **Benefit**: from "estimate" to a real quotation with sheet/cutlist/hardware — the difference between a toy and a sales tool.

### 9. Perspective/homography utility
- **Compatible?** Yes, standalone and already TypeScript (`ALU SYS/src/utils/perspectiveTransform.ts` — 4-point homography via Gauss-Jordan → CSS `matrix3d`; `extractFlattenedImage` pixel-warp).
- **Difficulty**: Low. No dependencies; drop it in as `src/lib/perspectiveTransform.ts`.
- **Where**: a photo-upload → flatten-wall → (optionally feed AI image analysis) flow in the UI; `WallDrawingEngine2D` could use it to trace a photographed wall.
- **Benefit**: lets clients photograph a wall and get a plan-aligned flat image — a strong acquisition feature and a bridge to AI image analysis.
